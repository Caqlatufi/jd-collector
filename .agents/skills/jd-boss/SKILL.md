# BOSS直聘岗位 workflow

## 入口与边界

项目：`项目根目录`。先读取项目 AGENTS.md 及本 Skill 的 [公共操作规则](../platform-workflow.md)，按其顺序执行；不要要求用户操作“读取标签”。
平台代码：`BOSS`；官方主站：`https://www.zhipin.com/`。
领域适配：`frontend/src/account/adapters/platforms.ts` 中本平台配置；共享原生执行由 app 装配，不把 Electron 导入业务模块。

识别核心统一为 `gpt-6-astra` / `medium`；进行图片识别时完整读取 [标准Prompt](../jd-vision-prompt.md)。原生 capture/scroll/click/type 已接入；使用公共操作规则中的命令取图，不退回旧 DOM 读取。

## 本平台步骤

2026-09-11起，本轮默认采用列表批次初筛：拍一张列表，按可见卡片依次点击，各拍一张包含左侧选中卡片及右侧详情的原生图；主Agent只检查目标切换、图片可读与无私人内容，不在每卡之间做业务分析。每批1–8卡，明确cardId、listBbox、详情captureId，使用`node ops/recognition/screen.mjs <plan.json>`提交。后台Astra/medium先读列表；调度器以平台、标准化公司名和保留括号方向的完整岗位标题查询正式JD及更早完成的SCREEN_BATCH，明确重复时记录关联而不发送详情图；标题或公司被截断、方向不同或无法可靠匹配时继续读详情。非重复候选再只读对应详情，输出保留／排除／需补充。主控仍拍摄每张详情，查重只减少模型详情读取，不改变Electron操作和证据保留。单屏足够判断即结束，不因缺独立URL、公司介绍、通勤或用工信息自动补图；保留候选需正式归档时再补必要资料。详情错岗/未加载或缺口影响判断才补拍。此流程优先于下面完整DETAIL归档步骤，具体协议见公共规则与标准Prompt第5节。

1. 在项目 frontend 运行 `node src/app/electron/workflow.mjs BOSS open`，再 `BOSS tabs` 确认页面。
2. 若用户本轮只要求登录，保持页面打开交给本人，不擅自采集。本人登录/验证完成后才继续需要认证的操作。
3. 区域搜索先读本地平台任务单 `local/JD搜索任务单-BOSS.md`；尚未建立时参考 [公开任务单示例](../../../config/search-task.example.md)。按公共规则和已确认门槛设置并截图核验地点、经验、薪资、规模、学历及工作安排，再浏览列表。经验主搜与补搜档位以本地门槛和任务单为准；平台档位以当前页面为准，未支持的条件明确记缺口。公开官方域链接只作补充线索，不使用第三方摘要替代真实原文。
4. 用 `BOSS navigate "<已核实的官方岗位URL>" [key]` 定位，`BOSS tabs` 确认目标；focus 明确目标后 capture 取得原生图片，将同岗位1–4张图作为完整批次提交截图工作目录，由后端定时启动Astra/medium按标准Prompt识别；主Agent继续下一页。URL 必须属于本平台注册域；不编造搜索 API 或绕过验证。
5. 按公共规则核对后，只在用户授权采集/更新时走现有 JD HTTP 接口。报告链接、时间、缺口和已保存数量。

## 本平台真实性

原生截图、受限输入和旧 DOM 退役已实现。2026-09-09 已执行本平台真实详情 → Astra/medium → 主 Agent 对图复核 → 独立 H2 的真实 HTTP 保存、来源查重及状态回读。结果仅代表该样本与当次页面，不代表全站搜索覆盖、长期认证或所有岗位符合门槛。遇到登录、验证码、空页或无法辨识的图，停止相应操作交本人处理。

## 视觉操作要点

- 列表与右侧详情分开核对；标题点击可能只换右侧内容，不能把列表 URL 当来源。
- 需要完整来源时根据截图点“查看更多信息”进入独立详情，再用 tabs 取得新 key 与实际 job_detail URL；避开“立即沟通”。
- 独立详情向下分段取得正文和工作地址，裁去求职竞争力/个人资料区域。窄窗左裁可能丢失短标题，补拍时保留标题左边界。
- 本次验证包括从 Java 列表到独立详情；搜索、翻页坐标始终按新截图确定，不固定坐标。
