# BOSS 采集 SOP

当前采集仅使用 BOSS。本文件统一维护 BOSS 操作流程；[公共规则](../platform-workflow.md)维护连接、原生输入和保存契约，[识别 Prompt](../jd-vision-prompt.md)维护模型输入输出协议。当前条件、搜索范围和进度分别读取本项目 criteria API、`local/JD搜索任务单.md`及`local/JD搜索任务单-BOSS.md`，不在 SOP 中复制个人答案或历史进度。用户最新明确指令优先。

主流程：**读取条件与断点 → 设置变化项并核验 → 列表与逐卡预览截图 → 提交后继续采集 → 集中复核 → 查重、评分、保存与回读 → 更新本轮覆盖。**

## 1. 开始或接续

1. 读取根 AGENTS、公共规则、总任务单及 BOSS 任务单的本轮记录；识别前完整读取 Prompt。只登录的请求停在打开平台，不进入采集或写库。
2. 从本项目 `local/env.json` 核对后端、数据库、userData、管道、criteria、识别目录及查重接口；只操作本项目客户端。同客户端串行控制，另一独立项目可自行并行，不控制其页面或写其数据。
3. GET `/api/criteria` 读取有效门槛，GET `/api/recognition/config` 核对实际识别配置，默认 `gpt-6-astra / medium`，不自动换模型。评分前读取唯一启用 MASTER 列表及详情正文。
4. 在 `frontend` 用 `node src/app/electron/workflow.mjs BOSS tabs` 确认当前列表 key，capture 后实际看图；没有平台标签时才 open。历史窗口、key、坐标及截图均不能当作当前状态。已有成功批次和主审已解决项不重新提交。

## 2. 设置与核验筛选

在 `frontend` 使用 `node src/app/electron/filters/boss.mjs help`；入口支持 `capture / record / apply`，配方保存于本项目 `runtime/search-filters/BOSS/steps.json`。

- **已有适用配方**：复用当前已生效基础条件，只 apply 本组合变化项；不因接续或换词重新校准、重新遍历全部菜单。
- **首次使用、步骤缺失或布局变化**：主 Agent 看控件图，record 后 apply 校准受影响步骤；缺少步骤名时补齐平台 profile。入口存在不代表完整配方已验证。
- 完整设置顺序为 **地点 → 经验 → 薪资 → 规模 → 学历 → 全职**；档位来自本轮任务单与有效门槛。多选先明确旧状态，再取消旧选项并选择目标档，不盲 toggle。清空后面板关闭时显式重新展开。
- 使用 `apply --key <当前key> --steps <已校准步骤名列表>` 批量执行。执行器逐步 capture 并核验 PNG、平台、key、来源、视口、缩放及显示比例；主 Agent 不在每步之间重复人工检查。
- apply 后集中看真实选中状态，并核对关键词、地域及条件是否保留。`verified:false` 只证明动作发送；菜单按钮数量不能证明实际档位。条件未生效先恢复，再浏览。
- `STEP_NOT_CALIBRATED / RECALIBRATION_REQUIRED / LAYOUT_CHANGED / ANCHOR_CHANGED / STALE_CAPTURE` 停在具体步骤，读取返回图，只修复受影响步骤及其后续布局；不关闭校验、不盲重试整组、不自动退回逐项手动操作。

保留用户系统窗口位置、尺寸和屏幕，不移动、最大化或反复激活窗口。需要更多正文使用页内缩放，再重新 capture 并校准受影响坐标。后台工作不抢主窗口焦点；重启只用于必要升级，沿用既有授权并确认无未保存输入，不为测试关闭用户实例。

## 3. 采集并提交批次

1. 拍一张列表图，确定本批 1–8 张卡片及 `cardId/listBbox`。列表有明确排除证据或已有可靠身份与结论时，可简记后跳过；不做逐卡完整分析。剩余待初筛卡按以下流程拍预览。
2. 依次点击本批卡片；每卡拍一张**包含左侧选中卡片及右侧正文的完整视口图**。卡片之间主 Agent 只检查切换正确、图片可读及无私人内容，不评分、不补齐全部字段、不等识别结果。
3. 写完整映射计划，在项目根执行 `node ops/recognition/screen.mjs <plan.json>`。确认提交成功后继续下一批；运行中任务不重复启动，筛选菜单图不入队。
4. 后台按实际配置先读列表，再由调度器查询正式 JD 及更早完成批次；明确重复关联 `postingId` 或 `taskId/cardId`，不发送该卡预览给模型。公司或标题截断、身份冲突、方向不同均不能猜作重复，继续读取对应预览。

**默认始终留在列表预览**：禁止“查看更多信息”、另开职位标签、导航 `job_detail`，也不用公开搜索取得独立详情来补链接。采集或入库授权不构成例外；只有用户本轮明确要求独立详情核实时，才另按该授权核实。

## 4. 集中复核与补图

经 `/api/recognition/tasks` 读取结果；模型输出是初筛记录，`KEEP` 不表示门槛全部通过，`SUCCEEDED` 不表示已入库。主 Agent 按下面的判断集中处理：

| 情况 | 动作 | 留存 |
| --- | --- | --- |
| 完整身份确认重复 | 跳过，不覆盖旧 JD | 关联正式 JD 或历史候选；沿用已核实风险 |
| 有明确不符合门槛或方向的证据 | 排除，不为其补完整正文 | 具体原因和截图索引 |
| 错岗、未加载，或缺失内容会改变判断 | 在当前预览补必要图后复核 | 具体区域、原因及补图关联 |
| 值得保留，但身份或连续正文仍不足 | 留候选，不拼凑入库 | 缺口与后续断点 |
| 身份明确、连续正文齐全，已完成业务复核 | 进入查重、评分与保存 | 原文、证据及未确认业务事实 |

补图仅在当前右侧预览滚动或页内缩放；分段保留身份锚点和正文重叠。完整视口不等于完整滚动正文。URL、工商、公司介绍、通勤、用工或 HC 等图外信息缺失写待核，不因此反复截图或跳页；未知不能当作满足，也不能猜为不符合。图外缺口与正文不完整分开记录。

主审结论保存到任务目录 `review-resolution.json`，已解决项记录 `mainReview.status=RESOLVED`，保留模型原始输出。接续时同时看原始结果与主审结论，不因旧 `NEEDS_MORE/NEEDS_REVIEW` 重做已解决项。

## 5. 查重、评分、保存与回读

按[公共保存规则](../platform-workflow.md#5-保存与汇报)读取公司/Postings 契约，集中核对关键字段、正文和证据，依据真实 MASTER 评分。

- 已有真实职位 URL：先查 `/postings/source?url=...`。没有独立 URL：按 **平台＋公司＋完整标题** 核对正式库及历史候选，`sourceUrl` 留空，记录截图来源和缺口。列表 URL、猜测 jobId 或伪造链接均不能填入来源字段。
- 标题截断或身份冲突先补身份；重复跳过不覆盖，匹配已有公司后保存新增 JD。
- 新增保持 `SCREENED`，无 `nextAction`。有证据的字段与评分写清依据，通勤、用工、HC 等未知事实保留待核，不伪装成已确认合格。
- 保存后回读核对身份、原文、评分、阶段与缺口；回读完成才计真实新增。不得自动投递、联系 HR、上传简历或排跟进。

## 6. 记录覆盖与停点

只更新 BOSS 任务单本轮记录：实际地点、词、经验及生效档位、首末屏、终点或停止原因、批次及候选处理结果。总任务单只作导航和范围规则，接续文件只作摘要与下一步入口；详细进度不多处复制。

按总任务单约定判断组合完成，区分零结果、页脚、反馈区、连续两屏无新相关线索、验证受阻和未完成；不把推荐区或卡数当作全站穷尽。9月历史完成不代表10月增量完成。登录、验证码交用户处理，保留断点后继续本轮其他可推进组合。

汇报分别列出真实新增、重复、排除、候选待核及未覆盖范围；卡片观察数、识别卡数、唯一岗位数不能混算。构建或夹具测试通过不能作为实际平台覆盖证据。

## 批次计划格式

`plan.json` 包含 `taskId`、当前有效 `criteria`、`list:{manifest,captureId?}`、`cards:[{cardId,listBbox,detail:{manifest,captureId?}}]`，最多8卡。`manifest` 路径相对计划所在目录，多图 manifest 必须指定 `captureId`；`listBbox` 为列表 PNG 的 `[x,y,width,height]`，归一化0–1。提交器从原生 manifest 复制元数据，不手改尺寸、时间、哈希或来源。每卡初次一张预览；需要连续正文时另提交同岗 DETAIL 补图，协议见 Prompt。

原生命令、30秒动作时效、坐标转换、像素校验和有限重试见[公共规则第6节](../platform-workflow.md#6-原生命令与证据校验)。模型超时、失败和重试由异步队列处理，见[识别模块](../../../docs/04-JD采集与截图识别.md#后端异步识别模块)，不在采集循环手动重复启动。
