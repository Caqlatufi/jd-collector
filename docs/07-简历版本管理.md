# 简历版本管理

管理一个标准Master、AI应用/Java后端/平台工程派生版及必要定向版，负责版本身份、启停和投递关联。Markdown正文、切片、A4预览与PDF输出独立维护在[简历编辑与PDF输出](08-简历编辑与PDF输出.md)。两个功能复用同一版本实体，不因文档拆分新建服务或表。

## 1. 需求分析

### 对象、目标和范围

候选人维护适用于不同方向的版本，Codex协助整理标准版和派生材料。标准版以最新版Word事实为基础，不编造经历；内容初始化由编辑输出功能承接。本功能保证投递可选择适用版本、历史关联不中断。

| 需求 | 规则 |
| --- | --- |
| 版本类型 | MASTER、AI_APPLICATION、JAVA_BACKEND、FULL_STACK、PLATFORM_ENGINEERING、TARGETED |
| 版本元数据 | 名称、版本标签、启用状态、说明；正文和照片/模板的编辑协议见独立编辑功能 |
| 唯一Master | 同时只有一个启用MASTER；启用另一个时停用原Master |
| 使用范围 | 停用版本不用于新投递，不删除既有岗位和历史使用引用 |
| 归档 | 独立 archived 状态，不设置 deleted，不改变正文与投递关联；默认列表及新投递选择隐藏，JD详情和Pipeline仍显示名称并可查看正文 |
| 版本详情 | 列表显示摘要，点击进入对应版本编辑页，不依赖展示外部DOCX路径 |
| 卡片说明 | 默认最大高度120px；实际溢出的说明显示“查看”，展开后最大高度320px并可滚动阅读，按钮切换为“收缩”。各卡片独立展开；说明和按钮操作不跳转编辑页，短说明不显示切换按钮 |
| 兼容 | 现有ID、类型与关联保留；旧relativePath只作内部兼容 |
| Master事实同步 | Master中的公司、项目、规模、指标或职责修正后，逐份复核全部有效派生版并同步受影响表述；更新版本标签并回读正文和切片 |

不建设DOCX文件管理、云盘或版本二进制仓库。版本关联不等于不可变内容快照，编辑正文后历史ID关联仍保留，不宣称额外存在快照能力。成功标准为唯一Master、版本选择和历史关联正确；工作量包含在编辑输出原估算中，不重复累计。

## 2. 架构设计

### 链路和职责

```text
简历列表 → 版本元数据/启停 → ResumeVersionService → jd_resume_version
投递记录 ─────────────────────────────────────────→ resumeVersionId
点击版本 → 简历编辑与PDF输出功能
```

版本管理拥有name/type/versionLabel/active/notes的业务语义。内容编辑拥有Markdown、模板、照片与派生切片；保存仍由既有ResumeVersionService统一校验和事务处理，不拆出相互覆盖的写入口。

```text
frontend/src/resume/{pages,api,index.ts}             版本列表与编辑入口
backend/resume/src/main/java/com/jd/resume
├─ model/ResumeVersion.java, ResumeDtos.java        共享版本实体/契约
├─ service/ResumeVersionService.java                版本保存、Master规则
└─ ctrl/ResumeVersionController.java                现有版本API
backend/pipeline                                    保存投递选择的版本引用
```

文档拆分无数据库变更。启停不能级联删除投递引用；跨功能共享的完整保存请求以编辑输出开发方案为唯一契约清单。

## 3. 开发方案

### 元数据模型

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| id | Long | 已有记录是 | 保留既有标识和投递关联 |
| name | String(120) | 是 | 版本名称 |
| type | Enum | 是 | MASTER/AI_APPLICATION/JAVA_BACKEND/FULL_STACK/PLATFORM_ENGINEERING/TARGETED |
| versionLabel | String(50) | 是 | 版本标签 |
| active | Boolean | 否 | 新保存默认true；受唯一Master约束 |
| archived | Boolean | 否 | 默认false，历史空值按未归档；仅由归档动作修改，普通编辑保留 |
| notes | TEXT | 否 | 适用岗位及版本说明 |

### 查询与保存

GET /jd-collector/api/resume-versions支持active、type，返回摘要数组：id/name/type/versionLabel/templateKey/photoUrl/active/notes/blockCount/createdAt/updatedAt；不返回Markdown正文。GET /resume-versions/{id}返回详情。

默认列表排除已归档项，摘要及详情返回 archived。POST /resume-versions/{id}/archive 仅设置 archived=true，有投递关联也可归档；详情与内容块仍可读取。原投递推进允许保留原归档简历，新投递不能选择归档版。列表卡片提供归档按钮；JD详情与Pipeline提供所用简历的查看链接。DELETE /resume-versions/{id} 为独立逻辑删除操作，归档不调用它。

POST /jd-collector/api/resume-versions与PUT /resume-versions/{id}仍使用[编辑输出的完整保存请求](08-简历编辑与PDF输出.md#3-开发方案)。修改元数据时须保留现有正文、模板和照片；本功能不新增只传active的PATCH接口，也不假定省略字段等于保留。

服务校验枚举、长度及Master规则；启用新Master与旧Master停用保持一致。40001为非法字段，40401为版本不存在，40901为版本状态/Master冲突，50001为保存异常。返回统一响应。

### 交付边界

版本列表与[投递功能](09-投递记录与跟进.md)共享真实resumeVersionId。元数据与内容更新沿用同一服务，不重复生成Vue模板。运营措辞调整与新增版本不引入数据库迁移；Markdown版本升级的历史迁移说明见编辑输出文档。

## 4. 验收方案

### 范围与标准

准备已有启用Master、第二个Master和一条可识别投递引用；数据写入使用独立测试环境。Codex验证接口与最终状态，候选人确认版本选择和使用记录。P0全部通过；不把文件列表可见当作版本关联已验证。

| 编号 | 优先级 | 场景 | 前置条件 | 操作 | 预期结果 | 责任角色 |
| --- | --- | --- | --- | --- | --- | --- |
| RES-211 | P0 | 唯一 Master | 已有启用 Master | 启用另一 Master | 原 Master 停用 | Codex |
| RES-212 | P0 | 投递兼容 | 版本已被投递引用 | 编辑正文并返回岗位 | 历史版本关联仍存在 | 候选人 |

### 验证说明

个人数据库操作、真实岗位样本与历史验收证据保存在本地 `local/private-docs/`。公开仓库的测试使用隔离夹具；实际验证范围以测试输出为准。
