# JD管理与评分

管理已录入JD的事实、来源、评分、档位、筛选和删除；每JD知识词和跨JD加权共现见[JD知识图谱](16-JD知识图谱.md)，截图获取及候选复核见[JD采集与截图识别](04-JD采集与截图识别.md)，实际投递后的状态归[投递记录与跟进](09-投递记录与跟进.md)。采集保存不等于投递。

## 1. 需求分析

### 列表工具栏

JD列表只保留关键词、阶段和查询按钮，以及知识图谱、JD门槛和新增JD入口。移除公司、岗位方向、等级、排序选择器及导出CSV按钮。默认保持BOSS竞争力降序；既有公司页、看板的查询链接继续兼容，不删除岗位字段或查询API。

搜索框支持公司名称、岗位标题或JD原文的包含匹配，忽略大小写及关键词首尾空格；公司名称使用公司库当前名称。输入后按回车立即查询，与点击查询按钮共用提交逻辑；清空关键词或改变阶段后立即查询。关键词写入查询地址，刷新保留。请求失败保留输入与已有列表，允许重试；页面在720px宽度下可操作。

“新增 JD”改为链接收录：弹窗只有一个 BOSS 岗位详情链接字段和“开始收录”，不再要求先创建公司或手填原文/评分。任务显示等待、读取、保存及具体失败原因，关闭弹窗不取消任务，再打开可查看持久化记录。登录/验证码由本人在收录标签完成，点击继续；其他失败可重试。完整性、查重、唯一启用 MASTER 评分与 SCREENED 保存契约见[JD采集与截图识别](04-JD采集与截图识别.md#链接自动收录)。已有公司和岗位不因新任务被覆盖；服务端原有 JD 保存接口继续供 AI 使用。

JD 列表将“方向”列替换为“BOSS 竞争力”，仅展示平台报告顶部的两项内容：`1534 / 2143 人`、`超过 28.42% 竞争者`。原方向字段继续用于筛选、编辑和评分。用户授权采集后，主 Agent 在有 BOSS 岗位直链的原页点击完整竞争力报告并截图，子 Agent 自行视觉读取这两项内容后保存；不采集报告中的雷达图、学历、薪资等明细。无直链显示“无 BOSS 直链”，尚未采集显示“未采集”，有截图确认但没有报告或岗位关闭时分别显示“无竞争力报告”“岗位已关闭”，不编造数值。

行操作新增“打招呼”，按当前 JD 和用户选择的简历生成首次沟通用语，支持编辑和复制。完整契约见[打招呼用语生成](17-打招呼用语生成.md)。

岗位名称可点击打开对应JD详情抽屉，支持键盘操作，悬停时显示链接样式。列表操作列移除“详情”和“编辑”，同时移除既有JD手动编辑表单的入口与分支；岗位原文、资料及五维评分由AI收录后通过既有接口维护。操作列保留打开JD/填写链接、打招呼、投递及红色“归档”，通勤及阶段仍使用各自入口。详情展示原文、评分依据、技能风险、阶段历史与面试记录。

点击红色“归档”后隐藏该岗位，正常列表、搜索、导出、看板、Pipeline及知识图谱不再显示，刷新后仍保持隐藏。归档使用既有deleted标记，保留数据库里的JD原文、评分、投递事实及关联历史，不改变阶段为CLOSED，也不物理删除数据。仅在后端成功后移除当前行并回读列表；请求期间防止重复归档及同一行阶段修改，失败保留该行并显示错误。当前不新增归档列表或恢复入口。

行操作有链接时提供“打开 JD”，按保存的 `sourceUrl` 在 Electron 顶部打开并激活岗位原页，方便手动沟通和投递。每个岗位使用固定标签 key，重复点击复用标签；沿用平台持久化登录分区。没有链接时提供“填写链接”，用户粘贴岗位地址后保存，按钮立即变为“打开 JD”，刷新后保留；打开或保存失败显示错误，可重试。缺失链接由用户手动补充，不启动自动查找或异步补链流程。

“记录投递”弹窗仅填写实际使用简历、实际投递时间和投递备注，不提供下一步动作或时间，也不在首次投递请求中提交这两个字段。定时跟进需求留待后续独立设计。

### 背景、目标与对象

候选人需要把不同方向的 JD 转成可比较、可解释的数据，并按匹配、公司、新鲜度、通勤、薪资决策。

### v0.1 范围与核心需求

录入 JD 原文、来源、地点、薪资、经验、技术项和招聘时间；计算五维总分、等级、风险和建议；支持搜索、筛选、评分降序、点击岗位名称查看详情与投递入口。既有JD不提供手动编辑入口，AI收录与评分接口继续使用。

通勤列第一行显示时间，第二行仅显示用户填写的备注（备注为空则不显示第二行）。没有时间时显示“未填写”，可直接填写单程分钟数上下限和可选备注并提交；已有时间也可修改。列表和详情共用同一入口。手动提交即完成填写，按范围上限重新计算通勤分、总分与自动等级，刷新当前筛选和评分排序；投递阶段不变。当前没有后续通勤核验流程或地图API，页面不显示“未核验/待核验”状态。

未投递岗位的“阶段”提供行内下拉框，可选择已收集、已筛选、待沟通、已发消息未回复、等待进一步沟通、已沟通不合适、待投递和已关闭。选择后立即保存，刷新仍保留，并支持按阶段筛选。JD 列表移除“下一步”列；详情和 Pipeline 继续承载已有跟进信息。已投递及后续阶段不提供下拉框，阶段文字可点击跳转对应投递记录；保留投递时间的关闭岗位同样可查看历史。已投递行隐藏“打招呼”和“已在 Pipeline”，未投递行保留打招呼与符合条件的投递按钮。跳转携带岗位名称 `keyword` 与精确定位 `postingId`，同名岗位也能直接看到对应记录。

### 本期边界与能力边界

- 默认包含 Java 后端、平台后端、AI 应用、全栈、AI 工具、测试平台开发。链接收录 graph 优先匹配已有分类；全部不适用时，可随 JD 自动新增岗位方向，详见[采集识别](04-JD采集与截图识别.md)。
- 新 JD 为 `SCREENED`，不等于投递，不生成计划。
- 不后台批量抓取、不自动投递；岗位只保存当前有效的地点和通勤评分结论。
- 无效、错配、资格硬性不符且不再需要决策的 JD 使用逻辑删除隐藏，不进入正常列表、看板、导出和知识图谱。
- `CLOSED` 只表示岗位或求职流程已经结束，仍保留在正常列表中；不能仅凭 `CLOSED` 推断 JD 无意义，也不能代替逻辑删除。

### 后台、兼容、成功与工作量

Agent 采集：用户以自然语言提出条件；平台 workflow 提供来源与岗位正文，由 Agent 核对公司、方向、评分和通勤证据后通过 posting 保存。只读请求不写库，保存不进入 Pipeline；不再经过账号页预览或转草稿。

JD 页负责关键词/阶段筛选、等级颜色和投递按钮。旧数据阶段继续兼容；页面默认按 BOSS 竞争力降序，既有链接中的筛选与排序参数保持兼容，页面不再提供排序选择器。没有指定排序参数的 API 调用继续使用 `totalScore DESC,id DESC`。3 分钟内完成录入、规则正确且未投递不进 Pipeline 即达标，预计 1–2 日。

## 2. 架构设计

### 架构与链路

```text
frontend/posting -> Controller -> PostingService -> Repository -> jd_posting
 company ------------------------^ companyId
 pipeline/dashboard/export <-----^ 岗位快照
录入 -> 校验 -> 五维求和 -> 默认等级/建议 -> 人工覆盖校验 -> SCREENED
```

投递前进度由 posting 页面调用 pipeline 的阶段服务，在同一事务内保存岗位与阶段历史；不设置投递时间或简历，不进入 Pipeline。请求携带当前观察到的阶段，并对岗位加写锁，防止并发沟通修改覆盖实际投递记录。

岗位原页入口通过 `common/desktop/client` 调用既有 `browser.open`，key 为 `posting:<id>`。主进程负责地址校验、平台会话分区和顶部标签复用；网页模式显示公共客户端的桌面使用提示。该操作不修改岗位或投递状态。

### 规则矩阵

Agent workflow → 平台适配读取候选 → Agent 核对公司、来源和评分 → 原 posting HTTP 保存链路。account 不依赖 posting 页面；删除跨模块草稿事件，候选不新增数据库表。

| 规则 | 口径 |
| --- | --- |
| 分数 | 35+20+15+15+15=100 |
| 等级 | ≥80 S、≥65 A、≥50 B，否则 SKIP |
| 阻断 | `blockingRisk=true` 强制 SKIP |
| 覆盖 | 改等级/建议必须有原因 |
| 通勤 | 出发地、方式与时间要求由本地 JD 门槛配置 |
| 手动通勤计分 | 按分钟范围上限：≤30分钟15分、≤45分钟12分、≤60分钟10分、>60分钟0分；范围45–55计10/15；仅在手动提交时触发，不批量重评历史记录 |
| 局部重算 | 其他四项分数保持；总分重新求和，自动等级沿用80/65/50；有原因的人工等级和建议覆盖保留，阻断风险仍强制SKIP；评分不等于HC/办公点核验通过 |

### 核心数据模型

| 组 | 字段 | 类型/约束 |
| --- | --- | --- |
| 基础 | companyId,title,direction,source,sourceUrl,rawJd,location | ID；160；注册分类编码 varchar(40)；来源枚举；1000；Text；255 |

## 3. 开发方案

### 目标、范围、职责与顺序

交付 JD CRUD、评分和列表：模型/Repo → 评分服务 → 接口 → 表单/列表 → 投递入口。依赖 company 和 foundation；不负责阶段推进。

### 数据模型

保存请求包含架构文档中从 `companyId` 到 `manualOverrideReason` 的业务字段；必填：companyId、title、direction、source、rawJd、五维分。响应增加 totalScore、tier、recommendation、Pipeline 快照、companyName、resumeVersionName 和时间字段。

方向：`JAVA_BACKEND/PLATFORM_BACKEND/AI_APPLICATION/FULL_STACK/AI_TOOLING/TEST_PLATFORM`；本轮采集来源：`BOSS`（字段完整契约以现有后端 DTO 为准）；建议：`DIRECT_APPLY/CONTACT_FIRST/CUSTOM_DEMO/WAIT_HC/SKIP`。

### 接口

| 方法 | 路径 | 请求/返回 |
| --- | --- | --- |
| GET | `/jd-collector/api/postings` | keyword(公司名称/标题/JD)、direction[]、tier[]、stage[]、companyId、resumeVersionId、sortBy(SCORE/BOSS_COMPETITION，API默认SCORE)、number、size≤100；分页结果 |
| GET | `/jd-collector/api/postings/{id}` | ID；完整岗位 |
| GET | `/jd-collector/api/postings/source` | 必填url；trim后来源精确匹配，非删除岗位Response[] |
| POST | `/jd-collector/api/postings` | 保存请求；新岗位 `SCREENED`；重复非空来源HTTP409/code40901 |
| PUT | `/jd-collector/api/postings/{id}` | ID+保存请求；更新评分 |
| PUT | `/jd-collector/api/postings/{id}/archive` | 岗位ID、无请求正文；加写锁后标记deleted=true，返回true；不存在或已归档返回404，保留评分、阶段、投递与历史数据 |
| PUT | `/jd-collector/api/postings/{id}/commute` | `minMinutes/maxMinutes` 必填，0–1440整数且下限≤上限；`note` 可选单行≤300字；`expectedRiskNotes` 必填（无备注传空串）；返回完整岗位，备注过期返回409 |
| PUT | `/jd-collector/api/postings/{id}/source-url` | `sourceUrl` 必填，HTTPS且≤1000字；`expectedSourceUrl` 必填，无链接传空串；更新来源链接并在链接变化时清空旧竞争力快照，不改正文/评分/投递事实，返回完整岗位；过期或其他岗位已用链接返回409 |
| PUT | `/jd-collector/api/postings/{id}/boss-competition` | `expectedSourceUrl/status/checkedAt/evidencePath` 必填；AVAILABLE 时 `rank/competitorCount/surpassedPercent` 三项完整；UNAVAILABLE/CLOSED 时不填三项数值且 `note` 必填；仅接受HTTPS的 zhipin.com/www.zhipin.com 岗位详情直链，原链接过期返回409；返回完整岗位 |
| PUT | `/jd-collector/api/postings/{id}/contact-stage` | `toStage`、`expectedStage` 必填；仅允许投递前阶段；返回更新后的岗位；阶段过期或已投递返回 HTTP 409 |

错误：40001 字段/枚举/分数非法，40401 公司或岗位不存在，40901 范围倒挂或覆盖无原因。

### 页面、部署、风险与完成

Agent 使用原 POST /api/postings 保存已核对的岗位；保存前 GET /api/postings/source?url=... 查重，不静默覆盖已有记录。公司ID、方向、正文和评分按后端 DTO 补齐，证据缺失不编造；本轮新增使用 BOSS 来源。新增保持 SCREENED，无跟进或投递时间。原手工 JD 编辑表单保留，账号页转草稿事件链路删除。

列表默认按 BOSS 竞争力降序并区分等级颜色，提供排序选择、点击岗位名称查看详情、导出、投递和归档。竞争力排序按截图的 `bossSurpassedPercent` 从高到低，百分比相同按 `bossRank / bossCompetitorCount` 从低到高，再按总分和 ID 降序保证稳定；只有 AVAILABLE 且数值完整有效的报告参与，0% 排在未采集、无报告和岗位关闭之前。排序在后端分页前执行，CSV 导出使用同一口径；切回综合评分时按总分和 ID 降序。随一体化部署。来源和办公点过期需重新核验评分。未点击投递的 JD 不进入 Pipeline/时间图即完成。

竞争力保存由专用接口在岗位写锁和同一事务内完成，不提交整份 JD，不修改原方向、正文、评分、沟通阶段或投递事实。百分比按截图原值存储，不由排名另行推算。来源链接变更时清空旧竞争力快照以免错岗；链接未变的正常编辑保留报告。采集时间和简短说明仅用于提示，证据路径不进入公共岗位响应。列表与详情使用同一个两行展示组件，0% 仍正常显示。

`PostingCommute` 负责通勤展示与范围表单，提示计分规则。提交调用独立局部更新接口，加岗位写锁并核对原风险备注，把新的 `【通勤估算】`、`【通勤备注】`、`【通勤评分】` 前置到风险说明，保留完整原备注、地址和路线证据；在同一事务内重算通勤分、总分和自动等级。人工覆盖按修改前默认等级和建议识别，保留有效原因；阻断风险仍优先。页面展示返回的分数并回读列表，以正确更新排序和等级筛选。失败保留输入，提交期间禁止重复提交；空备注保存空标签，避免回退到历史备注；兼容隐藏早期自动生成的“手动填写，待核验”，编辑时也按空备注展示，不批量修改个人数据。历史研究中的通勤状态仅留在原风险备注，不作为当前填写流程的状态。

采集时其他分项及历史通勤分仍来自Agent/人工评估后传入保存请求。原有内部计算只负责求和、分档；新增的分钟计分规则专用于手动通勤提交，不调用模型。
