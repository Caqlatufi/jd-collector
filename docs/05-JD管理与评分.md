管理已录入JD的事实、来源、评分、档位、筛选和删除；每JD知识词和跨JD加权共现见[JD知识图谱](16-JD知识图谱.md)，截图获取及候选复核见[JD采集与截图识别](04-JD采集与截图识别.md)，实际投递后的状态归[投递记录与跟进](09-投递记录与跟进.md)。采集保存不等于投递。

## 1. 需求分析

### 背景、目标与对象

候选人需要把六类目标 JD 转成可比较、可解释的数据，并按匹配、公司、新鲜度、通勤、薪资决策。

### v0.1 范围与核心需求

录入 JD 原文、来源、地点、薪资、经验、技术项和招聘时间；计算五维总分、等级、风险和建议；支持搜索、筛选、评分降序、详情、编辑与投递入口。

### 本期边界与能力边界

- 只收 Java 后端、平台后端、AI 应用、全栈、AI 工具、测试平台开发。
- 新 JD 为 `SCREENED`，不等于投递，不生成计划。
- 不后台批量抓取、不自动投递；岗位只保存当前有效的地点和通勤评分结论。
- 无效、错配、资格硬性不符且不再需要决策的 JD 使用逻辑删除隐藏，不进入正常列表、看板、导出和知识图谱。
- `CLOSED` 只表示岗位或求职流程已经结束，仍保留在正常列表中；不能仅凭 `CLOSED` 推断 JD 无意义，也不能代替逻辑删除。

### 后台、兼容、成功与工作量

Agent 采集：用户以自然语言提出条件；平台 workflow 提供来源与岗位正文，由 Agent 核对公司、方向、评分和通勤证据后通过 posting 保存。只读请求不写库，保存不进入 Pipeline；不再经过账号页预览或转草稿。

JD 页负责组合筛选、等级颜色和投递按钮。旧数据阶段继续兼容；默认按 `totalScore DESC,id DESC`。3 分钟内完成录入、规则正确且未投递不进 Pipeline 即达标，预计 1–2 日。

## 2. 架构设计

### 架构与链路

```text
frontend/posting -> Controller -> PostingService -> Repository -> jd_posting
 company ------------------------^ companyId
 pipeline/dashboard/export <-----^ 岗位快照
录入 -> 校验 -> 五维求和 -> 默认等级/建议 -> 人工覆盖校验 -> SCREENED
```

### 规则矩阵

Agent workflow → 平台适配读取候选 → Agent 核对公司、来源和评分 → 原 posting HTTP 保存链路。account 不依赖 posting 页面；删除跨模块草稿事件，候选不新增数据库表。

| 规则 | 口径 |
| --- | --- |
| 分数 | 35+20+15+15+15=100 |
| 等级 | ≥80 S、≥65 A、≥50 B，否则 SKIP |
| 阻断 | `blockingRisk=true` 强制 SKIP |
| 覆盖 | 改等级/建议必须有原因 |
| 通勤 | 出发地、方式与时间要求由本地 JD 门槛配置 |

### 核心数据模型

| 组 | 字段 | 类型/约束 |
| --- | --- | --- |
| 基础 | companyId,title,direction,source,sourceUrl,rawJd,location | ID；160；六类枚举；来源枚举；1000；Text；255 |
| 薪资经验 | salaryMinK/MaxK/Months, experienceMin/Max | 非负、范围不倒挂，月数1–24 |
| 新鲜度 | publishedAt,recruiterActiveAt,officialSynchronized | Date、Date、Boolean |
| 分析 | requiredSkills,bonusSkills,matchPoints,skillGaps,riskNotes | Text |
| 评分 | 五维分、blockingRisk,totalScore,tier,recommendation | 范围见规则，总分后端计算 |
| 覆盖 | manualOverrideReason | String(500) |
| 快照 | stage,resumeVersionId,appliedAt,nextAction,nextActionAt | 由 pipeline 管理 |
| 隐藏归档 | deleted | 基础实体逻辑删除标记；与 stage 独立，不作为求职流程阶段 |

### 目录与存储

图例：`[+]` 新增，`[~]` 修改，`[-]` 删除。

```text
backend/posting/src/main/java/com/jd/posting/{[~] ctrl,model,repo,service}
frontend/src/posting/{[~] api,pages,index.ts}
```

`jd_posting` 由 JPA DDL 管理，无迁移脚本。

## 3. 开发方案

### 目标、范围、职责与顺序

交付 JD CRUD、评分和列表：模型/Repo → 评分服务 → 接口 → 表单/列表 → 投递入口。依赖 company 和 foundation；不负责阶段推进。

### 数据模型

保存请求包含架构文档中从 `companyId` 到 `manualOverrideReason` 的业务字段；必填：companyId、title、direction、source、rawJd、五维分。响应增加 totalScore、tier、recommendation、Pipeline 快照、companyName、resumeVersionName 和时间字段。

方向：`JAVA_BACKEND/PLATFORM_BACKEND/AI_APPLICATION/FULL_STACK/AI_TOOLING/TEST_PLATFORM`；来源：`BOSS/LIEPIN/OFFICIAL/OTHER`；建议：`DIRECT_APPLY/CONTACT_FIRST/CUSTOM_DEMO/WAIT_HC/SKIP`。

### 接口

| 方法 | 路径 | 请求/返回 |
| --- | --- | --- |
| GET | `/jd-collector/api/postings` | keyword(标题/JD)、direction[]、tier[]、stage[]、companyId、resumeVersionId、number、size≤100；分页结果 |
| GET | `/jd-collector/api/postings/{id}` | ID；完整岗位 |
| GET | `/jd-collector/api/postings/source` | 必填url；trim后来源精确匹配，非删除岗位Response[] |
| POST | `/jd-collector/api/postings` | 保存请求；新岗位 `SCREENED`；重复非空来源HTTP409/code40901 |
| PUT | `/jd-collector/api/postings/{id}` | ID+保存请求；更新评分 |

错误：40001 字段/枚举/分数非法，40401 公司或岗位不存在，40901 范围倒挂或覆盖无原因。

### 页面、部署、风险与完成

Agent 使用原 POST /api/postings 保存已核对的岗位；保存前 GET /api/postings/source?url=... 查重，不静默覆盖已有记录。公司ID、方向、正文和评分按后端 DTO 补齐，证据缺失不编造；JOB51/ZHAOPIN 使用 OTHER 来源并保留来源链接。新增保持 SCREENED，无跟进或投递时间。原手工 JD 编辑表单保留，账号页转草稿事件链路删除。

列表按评分降序并区分等级颜色，提供详情、编辑、导出、投递。随一体化部署。来源和办公点过期需重新核验评分。未点击投递的 JD 不进入 Pipeline/时间图即完成。
