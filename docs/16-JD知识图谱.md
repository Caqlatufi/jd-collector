# JD知识图谱

状态：首版已开发并完成数据回填，2026-09-12。本文承接[JD管理与评分](05-JD管理与评分.md)，统一维护需求分析、架构设计、开发方案和验收方案。

## 1. 需求分析

### 1.1 背景

当前工作台保存了每条JD的原文、方向、必选技术和加分项，但只能逐条阅读，无法看出多个岗位共同要求哪些知识。实际回填时以接口实时数量为准。岗位数量增长后，需要把每条JD拆成可复用的知识词，并按岗位侧重点赋予优先级，再对全部或部分JD计算交叉关系。图谱用于判断知识覆盖面和准备优先级，不改变现有岗位评分与投递状态。

### 1.2 需求目标

- 每条非删除JD独立持久化知识词，支持高、中、低三档优先级。
- 按选定JD集合动态计算知识词覆盖量和词之间的共现关系。
- 节点面积体现优先级加权后的交叉量，交叉越多、优先级越高，节点越大。
- 在JD列表提供入口，进入保留JD菜单高亮的二级页面。
- 首次上线完成现有全部JD的拆词回填，并能识别新增、更新后尚未拆词或已经过期的JD。

### 1.3 使用对象

本机工作台使用者负责查看图谱、选择JD范围和校正单个JD的知识词；Agent负责初次批量拆词以及后续新增JD的知识词生成。

### 1.5 核心需求

#### 1.5.1 单JD知识词

| 项 | 内容 |
| --- | --- |
| 输入 | postingId、title、direction、rawJd、requiredSkills、bonusSkills |
| 知识词范围 | 编程语言、框架、中间件、数据库、AI能力、工程实践、业务技术领域 |
| 排除内容 | 公司名、地点、薪资、年限、福利、招聘套话和“负责／熟悉／优先”等普通词 |
| HIGH | 核心职责或硬性能力，缺失会直接影响岗位胜任 |
| MEDIUM | 重要支撑能力、频繁使用的技术或主要协作能力 |
| LOW | 加分项、邻接工具或用于理解场景的领域知识 |
| 去重 | 同一JD内按标准词去重；多档重复时保留最高优先级 |
| 规模 | 每条JD最多30个知识词，HIGH建议3–8个、MEDIUM建议3–10个，其余进入LOW |
| 输出 | 词集的提取版本与源内容哈希，以及每个词的展示词、标准化词、优先级和权重 |

知识词保持原子性但保留有意义的组合，例如`Spring Boot`、`RESTful API`、`RAG`、`设备通信`。版本号、方向或语义不同的词不强行合并；常见书写差异通过别名规则归一，例如`SpringBoot`归一为`Spring Boot`。

#### 1.5.2 图谱计算

| 指标 | 公式 | 页面含义 |
| --- | --- | --- |
| 优先级权重 | HIGH=3，MEDIUM=2，LOW=1 | 体现同一个知识词在不同JD中的侧重点 |
| 节点JD数 | 包含该词的不同JD数量 | 原始交叉范围 |
| 节点加权值 | `Σ weight(term, posting)` | 决定节点面积 |
| 节点直径 | `基础值 + 比例 × √节点加权值` | 确保圆的面积近似正比于加权值 |
| 边JD数 | 同时包含两个词的不同JD数量 | 原始共现次数 |
| 边加权值 | `Σ min(weightA, weightB)` | 决定连线粗细，避免高低组合被过度放大 |

默认只显示至少出现在2条选中JD中的词、共同出现在至少2条选中JD中的边，最多显示加权值最高的80个节点。页面允许把阈值降为1查看单JD关系。

#### 1.5.3 JD选择与页面交互

- 默认选择全部非删除JD，包括已关闭记录；页面显示“已选择／已处理／有词／过期”数量。
- 关键字、方向、等级和阶段用于缩小JD列表；“选择当前结果”只影响过滤后的JD。
- 点击节点显示三档来源分布以及包含该词的JD；点击边显示同时包含两个词的JD。
- 点击JD显示该JD三档知识词，并可整体替换后重新计算图谱。
- 未拆词或词记录过期的JD仍可被选择，但不贡献节点，页面明确显示数量和具体记录。

## 2. 架构设计

### 2.1 总体架构

```text
JD列表 /postings
└─ 知识图谱入口
   └─ 二级页面 /postings/knowledge-graph
      ├─ JD选择器
      ├─ ECharts知识图谱
      └─ 节点、边和单JD词详情

posting模块
├─ 现有JD事实与评分
└─ posting-knowledge能力
   ├─ 单JD词查询与原子替换
   ├─ 词源哈希与过期判断
   └─ 所选JD的节点、边实时聚合

Agent拆词任务
├─ 分页读取JD
├─ Astra/medium按JD输出三档知识词
├─ 协议校验与标准化
└─ 调用本地接口写入词集状态与jd_posting_term
```

### 2.2 关键规则

| 对象／场景 | 规则 | 生效条件 |
| --- | --- | --- |
| 单JD重复词 | 归一后只保留一条，档位取最高 | 替换词集合时 |
| 跨JD同义词 | 使用标准化词和受控别名合并 | 图谱聚合时 |
| 括号／版本 | 有实际语义的版本和方向保留 | 如Vue 2／Vue 3确需区分时 |
| 节点权重 | HIGH／MEDIUM／LOW分别贡献3／2／1 | 每个选中JD最多贡献一次 |
| 节点面积 | 与节点加权值近似线性 | 前端以平方根换算直径 |
| 边权重 | 每个共现JD贡献两词权重的较小值 | 两词同属一条选中JD |
| 空选择 | 返回0节点、0边和选择数0 | 请求显式传空postingIds |
| 默认选择 | 使用全部非删除JD | 请求不传postingIds |
| 过期 | 当前词源哈希与保存哈希不同 | JD参与拆词字段发生变化 |
| 图谱裁剪 | 先应用最小JD数，再按加权值取前80节点 | 默认展示 |

### 2.3 模块职责边界

| 模块 | 职责 | 数据／依赖 |
| --- | --- | --- |
| posting knowledge backend | 词存储、校验、归一、过期判断、图聚合 | `JobPostingRepository`、两张知识词表 |
| Agent extractor | 按单JD语义生成三档词并回填 | posting API、Codex CLI Astra/medium |
| posting frontend | 路由、JD选择、图表渲染、词详情与校正 | posting knowledge API、ECharts |

### 2.4 核心数据模型

#### 2.4.1 `JobPostingTermProfile`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | 是 | 主键 |
| postingId | Long | 是 | 所属非删除JD，一对一唯一 |
| extractorVersion | varchar(40) | 是 | 生成协议版本，首版`jd-term-v1` |
| sourceHash | char(64) | 是 | title、direction、rawJd、requiredSkills、bonusSkills的内容哈希 |
| generatedAt | datetime | 是 | 本次词集生成或人工保存时间 |
| createdAt／updatedAt／deleted | 基础字段 | 是 | 沿用项目实体约定 |

档案记录存在即表示该JD已经处理；即使知识词为空也保留档案记录，因此可以与“从未拆词”区分。一个JD只有一个当前档案，一个档案可以包含多个`JobPostingTerm`明细；档案是当前拆词结果的元数据，不是执行任务历史。

#### 2.4.2 `JobPostingTerm`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | 是 | 主键 |
| profileId | Long | 是 | 所属`JobPostingTermProfile`，多对一关联 |
| term | varchar(100) | 是 | 页面展示的标准知识词 |
| normalizedTerm | varchar(100) | 是 | 去空格、大小写和别名归一后的聚合键 |
| priority | varchar(20) | 是 | HIGH／MEDIUM／LOW |
| createdAt／updatedAt／deleted | 基础字段 | 是 | 沿用项目实体约定；整组替换使用物理删除旧派生词 |

| 约束 | 规则 |
| --- | --- |
| JD内唯一 | `profileId + normalizedTerm`唯一；由于一个JD只有一个档案，等价于同JD内唯一 |
| 数量 | 每个JD最多30条 |
| 权重 | 不存冗余数值，由priority固定映射3／2／1 |
| 生命周期 | JD逻辑删除后不参与查询；替换词集合在同一事务完成 |

#### 2.4.3 图谱传输模型

| 模型 | 关键字段 | 说明 |
| --- | --- | --- |
| PostingOption | postingId、companyName、title、direction、tier、stage、processed、termCount、stale | 页面选择列表 |
| GraphNode | id、label、documentCount、weightedCount、highCount、mediumCount、lowCount、postingIds | 一个标准知识词 |
| GraphEdge | source、target、documentCount、weightedCount、postingIds | 两个知识词的共现关系 |
| KnowledgeGraph | selectedPostingCount、processedPostingCount、taggedPostingCount、stalePostingCount、nodes、edges | 一次筛选结果 |

### 2.5 核心流程

#### 2.5.1 首次拆词与存储

```text
分页读取全部非删除JD
  -> 每批按postingId提交标题、方向和JD技术字段
  -> Astra/medium为每个JD输出HIGH/MEDIUM/LOW知识词
  -> 校验ID完整、档位合法、每JD不超过30词
  -> 后端标准化并将跨档重复提升到最高档
  -> 事务内更新词集状态并替换该JD旧词
  -> 回读词数量、档位和sourceHash
  -> 汇总缺失、失败与过期JD
```

#### 2.5.2 图谱查询

```text
页面选择JD集合和阈值
  -> 后端读取所选JD有效词
  -> 按normalizedTerm聚合节点
  -> 在每条JD内部生成无序词对并聚合边
  -> 应用最小JD数和最大节点数
  -> 返回稳定排序的节点、边及覆盖统计
  -> 页面以节点面积和边粗细渲染
```

#### 2.5.3 JD更新后的处理

```text
JD更新
  -> 已存词保留
  -> 查询时发现sourceHash不一致并标记stale
  -> Agent或用户重新生成／调整三档词
  -> 原子替换后stale消失
```

### 3.5 词存储模块

#### 3.5.1 关键流程

1. 校验postingId存在且未删除。
2. 校验terms数量不超过30、term非空且长度不超过100、priority合法。
3. 执行Unicode NFKC、空白和受控别名归一；同一normalizedTerm保留最高档。
4. 后端从当前JD五个参与字段计算sourceHash。
5. 事务内更新或新建词集状态，物理删除旧派生词并批量保存新词。
6. 返回排序后的三档词及最新状态；空词也保留词集状态。

#### 3.5.2 关键接口

| 方法 | 路径 | 请求 | 返回 | 说明 |
| --- | --- | --- | --- | --- |
| GET | `/jd-collector/api/posting-knowledge/postings` | keyword、direction[]、tier[]、stage[] | `PostingOption[]` | 返回全部可选JD及处理、词数和过期状态 |
| GET | `/jd-collector/api/posting-knowledge/postings/{postingId}/terms` | 路径ID | `PostingTerms` | 三档词、sourceHash、stale |
| PUT | `/jd-collector/api/posting-knowledge/postings/{postingId}/terms` | `ReplaceTermsRequest` | `PostingTerms` | 原子替换一个JD的全部词 |

`ReplaceTermsRequest`：

| 字段 | 类型 | 必填 | 约束／用途 |
| --- | --- | --- | --- |
| extractorVersion | string | 是 | 1–40字符；Agent首版`jd-term-v1`，人工保存使用`manual-v1` |
| terms | TermInput[] | 是 | 0–30项；空数组代表明确无知识词 |
| terms[].term | string | 是 | 1–100字符的知识词 |
| terms[].priority | enum | 是 | HIGH／MEDIUM／LOW |

`PostingTerms`除上述词列表外返回postingId、processed、sourceHash、stale、updatedAt；从未处理时`processed=false`且sourceHash为空，明确空结果时`processed=true`且terms为空。每个词增加normalizedTerm和weight。

#### 3.6.1 关键接口

| 方法 | 路径 | 请求 | 返回 | 说明 |

`GraphRequest`：

| 字段 | 类型 | 必填 | 默认值／约束 |

`KnowledgeGraph`：

| --- | --- | --- |

### 3.7 Agent拆词模块

#### 3.7.1 职责与协议

- `extract.mjs --all`分页读取全部非删除JD；`--pending`只处理未拆词或已过期JD；`--posting <id>`只处理指定JD。
- 每批最多8条JD，模型固定`gpt-6-astra`／`medium`，只附结构化文本，不访问网页或数据库。
- Prompt要求每个输入postingId恰好输出一项，分为HIGH、MEDIUM、LOW；不输出公司、地点、薪资和普通招聘词。
- 本地先校验整批ID完整性，再逐条校验词数量与格式并调用PUT接口；单条不合格只拒绝该条，合法同批记录仍保存，`--pending`可从真实断点重试。
- 首次回填记录总JD数、成功数、空结果数、失败数、各档词数及最终过期数。

#### 3.7.2 新增与更新衔接

Agent正式保存新JD后执行单JD拆词；JD正文或技术字段更新后重新拆词。人工页面创建或修改但未拆词时，知识图谱页面通过“未拆词／已过期”状态提示处理，不阻止原JD保存。

### 3.8 图谱页面模块

| 区域 | 功能 | 交付结果 |
| --- | --- | --- |
| JD列表工具栏 | “知识图谱”按钮 | 跳转`/postings/knowledge-graph` |
| 页面顶部 | 返回JD列表、刷新、选择统计、图例 | 路由和口径清晰 |
| 左侧选择器 | 四类筛选、全选、清空、选择当前结果、JD复选 | 支持任意子集 |
| 中部图谱 | 力导向图、缩放、拖动、节点与边点击 | 面积和线宽按后端值映射 |
| 右侧详情 | 节点、边或JD明细 | 能追溯到具体JD及三档词 |
| 词编辑器 | 三档词输入、去重提示、整体保存 | 保存后自动重算图谱 |

ECharts只负责布局和交互，节点、边、权重和阈值由后端返回；前端不复制业务聚合算法。

### 3.9 统一响应与错误码

沿用`RestResultResponse<T>`：成功`code=200`、`result`承载业务数据。

| HTTP状态 | 业务码 | 场景 |
| --- | --- | --- |
| 400 | 40001 | 词为空、档位非法、超过30词、请求JD超过500、阈值越界 |
| 404 | 40401 | postingId不存在或已删除 |
| 500 | 50001 | 未预期的存储或聚合失败 |

## 4. 验收方案

### 4.1 验收范围与前置条件

验收覆盖两张新表、单JD词接口、图谱计算、Agent回填、二级页面和现有JD兼容。前置条件：独立H2测试通过；本地应用健康；正式库已备份；现有非删除JD数量已记录；ECharts依赖已安装并锁定。

按项目约定不维护Bruno集合。API验收使用MockMvc集成测试和本机真实HTTP请求，分别记录测试库与个人业务库结果；构建通过不能替代真实HTTP和页面验收。

### 4.2 验收通过标准

- P0矩阵全部通过，数据库、API和页面统计一致。
- 首次回填覆盖全部非删除JD，失败数、未拆词数和过期数均为0；明确空结果单独计数。
- 固定夹具的节点和边可以按3／2／1及较低权重规则手工复算。
- 图谱筛选不修改JD评分、阶段、投递、面试或原文。
- 页面入口、直接打开、刷新、返回和720px以上布局可用。
